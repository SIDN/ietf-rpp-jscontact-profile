# Agents.md — IETF Internet-Draft

## Project Overview

This repository contains the IETF Internet-Draft for the **JSContact Profile for
the RESTful Provisioning Protocol (RPP)** (individual submission, targeting the
RPP working group). The document is authored in Markdown for mmark and compiled
to XML (xml2rfc v3), HTML, PDF, and TXT.

## Authoring Toolchain — mmark / Markdown

- Source format: Markdown for [mmark](https://mmark.miek.nl/) (CommonMark + extensions for RFCXML).
- Build (from `src/`): `make all` runs `mmark` → `.xml`, then `xml2rfc` → `.txt`/`.html`/`.pdf`/`.clean.txt`.
  Individual targets: `make xml`, `make txt`, `make html`, `make pdf`, `make nopagination-txt`.
  Requirements: [mmark](https://mmark.miek.nl/) and [xml2rfc](https://github.com/ietf-tools/xml2rfc#installation).
  Output lands in `docs/` (the `xml` target writes `../docs/<name>.xml`; the other targets read from there).
- mmark uses a TOML title block (between `%%%` fences) for document metadata
  (`title`, `abbrev`, `area`, `workgroup`, `submissiontype`, `keyword`, `date`,
  `TocDepth`, `[seriesInfo]`, `[[author]]`, …).
- mmark-specific syntax used in this draft: block attributes `{#anchor}` for
  cross-reference targets, `[@!RFCxxxx]` (normative) / `[@RFCxxxx]` (informative)
  citations, section markers `{mainmatter}` / `{backmatter}`, `.# Abstract` for
  the abstract, `{numbered="false"}` on back-matter headings, fenced `~~~ json`
  blocks with a following `Figure:` caption line, and `(#anchor)` cross-references.

## Conventions

### Literals

House style for literal tokens (JSContact member names, type names, enum values,
map keys, property values): render as inline code with the double-quotes **inside**
the code span, e.g. `"version"`, `"individual"`, `"org"`, `"contact"`. JSContact
**type** names appear as ordinary capitalized prose (Card, Address, EmailAddress),
matching RFC 9982. Apply this consistently on every edit.

### Cross-references and anchors

- Anchor: `{#my-anchor}` trailing a heading (e.g. `### Version {#version}`).
- Reference: `(#my-anchor)` (e.g. `(#profile-properties)`).
- Keep anchors stable: other sections and external readers may link to them.
  Never silently rename or drop an anchor during a restructure. Existing anchors:
  `version`, `kind`, `language`, `name`, `organizations`, `addresses`, `emails`,
  `phones`, `links`, `map-keys`, `localizations`, `profile-properties`,
  `jscontact-profile-registry`.

### Citations / references

- `[@!RFCxxxx]` / `[@!I-D.name]` for **normative**, `[@RFCxxxx]` for
  **informative**; mmark can auto-fetch reference XML from the IETF bibliography.
- Classify each reference as **Normative** or **Informative** deliberately — this
  affects the published RFC. The JSContact profiles specification is RFC 10050
  (`[@!RFC10050]`), formerly `I-D.ietf-calext-jscontact-profiles`.

### RFC 2119 / 8174 requirement keywords (markup)

Write the keywords in plain all-caps (`MUST`, `MUST NOT`, `SHOULD`, `MAY`, …), as
in the current source. The normative *meaning* of these words is covered under
**Writing Style → Normative language** below.

## Writing Style

IETF specifications have a distinct, conservative house style. Apply it to all
prose you add or edit. The goal is a document that an independent implementer can
turn into interoperable code without guessing.

### Normative language (RFC 2119 / BCP 14)

- Use **MUST / MUST NOT / REQUIRED / SHALL / SHALL NOT / SHOULD / SHOULD NOT /
  RECOMMENDED / NOT RECOMMENDED / MAY / OPTIONAL** only in their RFC 2119 sense,
  and **only in all-caps**. In lowercase these are ordinary English words with no
  normative force.
- The BCP 14 boilerplate lives in **Conventions Used in This Document**. It
  currently cites only RFC 2119; the full BCP 14 form should also cite **RFC 8174**
  with the "…when, and only when, they appear in all capitals" sentence — flag
  this when editing that section.
- Every normative keyword places a requirement on a **specific actor** for a
  **specific, testable behaviour** (here: the RPP client, the RPP server, or an
  RPP implementation). Name the actor.
- Don't stack keywords ("MUST … REQUIRED to …"); pick one. Don't use a keyword
  where plain present tense states a fact.
- Reserve **SHOULD** for genuine implementer discretion and say what to weigh; if
  there is no legitimate reason to deviate, it is a **MUST**.
- State **error handling and behaviour on receipt of malformed/unexpected input**
  explicitly (e.g. the validation-error rule in Profile Properties).

Per the **IESG Statement on Clarifying the Use of BCP 14 Key Words**
(<https://www.ietf.org/about/groups/iesg/statements/clarifying-use-bcp14/>):

- **Use the key words sparingly** — only where required for interoperability or to
  limit harmful behaviour. They are not for emphasis.
- A normative statement does **not** need a key word; plain declarative prose is
  equally normative. Prefer the plain form when a key word adds no clarity.
- **Justify every SHOULD / RECOMMENDED.** Spell out the reasoning and what a
  conformant implementation must consider before deviating.
- For **backward-compatibility** requirements, make the rationale explicit.
- **Do NOT use BCP 14 key words** in: the Abstract, IANA Considerations, examples,
  figures/captions, or appendices (a large *normative* appendix table is the only
  exception). The RFC Editor does not police this — it is the authors'
  responsibility. (The example Card figure and the IANA section correctly avoid
  key words.)

### Specify, don't describe

- Write **declarative, present-tense** requirements, not narrative or marketing
  prose. Define behaviour from the perspective of a **conformance target** (RPP
  client, RPP server) and name the actor in each requirement.
- Specify **both sides**: what a generator produces *and* what a parser must
  accept, including what a receiver does with unrecognised values.
- Give the **encoding precisely**: member names, allowed enum values, whether a
  member is mandatory/optional, and defaults (e.g. "when absent, the phone number
  is assumed to be a voice number").
- Prefer **explicit enumerations** over open-ended adjectives (the profile relies
  heavily on closed enum lists — keep them closed and exact).

### Terminology discipline

- Define each term **once**, in the Terminology section, then use it
  **consistently** — never introduce synonyms for a defined term.
- Reuse terminology from JSContact (RFC 9982/9553), RDAP (RFC 9083), and HTTP
  RFCs rather than reinventing it; cite the source and don't redefine borrowed
  terms.
- **Expand every acronym on first use** in both the body and any title (RPP,
  RDAP, JSContact/JSON, URL, BCP). RFC 7322 exempts well-known abbreviations
  (TCP, IP, HTTP, …).

### Structure and cross-references

- Lead each major section with a one-sentence statement of its purpose.
- Keep **rationale/history** in non-normative places (Introduction, notes,
  appendices); keep the normative body tight. Mark examples as non-normative.
- Cross-reference with anchors instead of repeating a requirement — duplicated
  normative text drifts out of sync. In particular, the per-property rules in
  **Using JSContact in RPP** and the **Profile Properties** table state the same
  constraints twice; when you change one, change the other and prefer linking.
- Use examples generously but keep them **consistent with the normative text** and
  labelled as illustrative.

### Document structure and required sections (RFC 7322)

Expected ordering: title, **Abstract**, status/copyright, ToC (front matter, from
the metadata block — the Abstract is yours to write); then Introduction →
Requirements Language → main technical sections → **IANA Considerations** →
Internationalization Considerations → **Security Considerations** → References;
back matter: Appendices → Acknowledgements → Contributors → Authors' Addresses.

Section-specific rules:

- **Abstract** — standalone; **MUST NOT contain citations or references**. The
  current abstract contains `[@!I-D.ietf-calext-jscontact-profiles]` and
  `[@!RFC9982]` citations — these should be reworded to prose references before
  publication.
- **IANA Considerations** — **required**. List every registry action precisely
  (registry, allocation policy, initial values). The JSContact Profile Registry
  entry is present but marked `TODO`; do not leave it as a bare TODO at submission.
- **Internationalization Considerations** — currently `TODO`; relevant here
  because the profile carries localized human-readable text (names, addresses).
- **Security Considerations** — **required**; currently `TODO`. Give the threat
  model per BCP 72 (RFC 3552); must be substantive before submission.
- **Privacy Considerations** — **strongly relevant** (this profile carries
  personal contact data: names, postal addresses, emails, phone numbers).
  Consider adding a section per RFC 6973 covering what personal data flows where,
  correlation/fingerprinting risks, and data minimisation.
- **References** — split **Normative** / **Informative**, ordered by tag, no
  introductory prose. Citation tags contain no spaces; a textual mention is
  "RFC 2119 [RFC2119]". (mmark generates the References section from citations.)

### Tone and mechanics

- Neutral and precise; avoid hype and hedging ("simply", "just", "obviously").
- Distinguish "i.e." (that is) from "e.g." (for example).
- One requirement per sentence where practical, to enable conformance checklists.
- Be **consistent** in spelling (American or British) throughout; use the serial
  (Oxford) comma (IETF default).
- **Capitalization:** title case for the document title and section titles; keep
  term capitalization consistent.
- **Figures** carry a `Figure:` caption and are referenced by number, not "the
  figure below"; no normative key words in captions.
- **Use reserved example values** (RFC 2606 / BCP 32: `example.com`,
  `example.net`, `.example`; RFC 5737 / RFC 3849 documentation IP ranges). The
  current example uses "Example Org" / "Joe User" and a real-looking street/city;
  prefer clearly-reserved placeholders where an identifier could resolve.
- Wrap bare URIs in angle brackets (`<https://example.com/>`).
- When in doubt about style, consult RFC 7322, the Chicago Manual of Style, and
  <https://authors.ietf.org/>; for keyword usage, RFC 2119, RFC 8174, and the IESG
  BCP 14 statement. Run **idnits** (or datatracker submission checks) before
  submitting.

## Edit Workflow

**CRITICAL**: All edits to the source document MUST follow this workflow. No
exceptions.

**CRITICAL — Never restore manually-removed content**: If the user has edited or
removed content directly in the source file, NEVER re-add, restore, or reintroduce
that content — not in a later edit, not as part of a larger replacement block, and
not when "fixing" something nearby. The user's manual edits are authoritative.
Before applying any edit, check that the surrounding text still matches the current
file (re-read the region if unsure) so an `old_string`/`new_string` block does not
silently bring back content the user has deleted. If an edit you are about to make
would reintroduce previously-removed text, stop and ask.

**CRITICAL — Bulk structural edits MUST be scripted**: Any change that repeats the
same structural transformation across many places (e.g. converting the Profile
Properties table to another form, rewrapping every entry in a list, re-quoting
every literal) MUST be done with a throwaway script (`.work-*.py` or similar), NOT
a series of hand-written `Edit` calls. The script:

- **Transforms structure only, never rewrites prose.** Parse the existing
  cells/lines and re-emit them verbatim; only table/list markup may change.
- **Is verified before trusting it.** Snapshot first
  (`cp src/draft-wullink-rpp-jscontact-profile.md /tmp/before`), run, then diff:
  confirm the prefix and tail are byte-identical and that only the intended
  structural tokens changed with **zero prose words changed**. Preserve all
  `{#anchor}` targets.
- **Respects manual edits.** Drive the transformation off the current file state
  and skip items the user already edited by hand.
- **Is deleted afterward** along with any `/tmp` snapshot. Do not commit
  `.work-*.py`.

Still follow the propose-and-approve steps below before running the script on the
live draft.

### Step 1 — Analyse and Propose

Before applying any change:

1. Read the relevant section(s) using the Document Index (`.agent-index.md`).
2. Always load the Terminology section for context.
3. Analyse the requested change and identify the best location(s).
4. Present a proposal to the user that includes: the target section (title +
   approximate line number), the exact content to add/modify/remove, and a brief
   rationale for the location.

### Step 2 — Await User Approval

- **Do NOT apply any edit** until the user explicitly confirms both content and
  location.
- If the user requests adjustments, revise and re-present before applying.
- Only after explicit approval, apply the edit and the Change History entry.

### Step 3 — Update the Index After Every Edit

After applying any approved edit to the source document:

1. **Regenerate the Document Index** by running `./update-index.sh` (auto-detects
   `src/draft-*.md`). The script rewrites `.agent-index.md` — do NOT edit the
   index or recompute line numbers by hand.
2. **Update the Terminology table** in Agents.md if the edit adds, removes, or renames a
   defined term.

Run `./update-index.sh` the same way when the user reports a manual change to the
source file noticed during a session (e.g. from a git diff or a comment).

### `update-index.sh`

`./update-index.sh` regenerates the Document Index by scanning the mmark source
for ATX headings (`#`..`######`, fenced-code-aware) and overwrites the
git-ignored `.agent-index.md` with the resulting table. It auto-detects the
source as the last `src/draft-*.md`; pass a path to override. The columns are
`Level | Title | Anchor | Lines`, where the range runs from the heading through
the line before the next same-or-shallower heading.
