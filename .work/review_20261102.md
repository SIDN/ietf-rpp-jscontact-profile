### Substantive defects

- [x] C01 (approved) L345 wrong actor: "Client validation MUST return an error if any JSContact properties other than those listed above are present." -> "An RPP server MUST reject a Card that contains a JSContact property not listed in this section."

Add "Property Name: version / Property Context: Card / Restricted Attributes: mandatory", or extend L342-343 to cover `"version"` like `"@type"`. (decision)
- [ ] C03 L207-261 RFC 9553 makes Card `"uid"` mandatory; the profile neither lists nor excludes it and the example omits it. Authors to confirm against RFC 9982 and state whether `"uid"` is required, ignored, or server-assigned. (verify)
- [ ] C04 L272 TODO / L274-340 Profile Properties omit restrictions stated normatively: Phone `"number"` (L140, MUST include), Link `"uri"` (L172), Address `"components"` (L128, locality required), EmailAddress `"address"`. Add "Restricted Attributes: mandatory" to these and drop the TODO comment. (decision on exact set)
- [ ] C05 L84 BCP 14 boilerplate lacks RFC 8174 -> "The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [@!RFC2119] [@!RFC8174] when, and only when, they appear in all capitals, as shown here."

Wrong: this document defines a profile, not RPP, and RPP itself is never cited. -> "RESTful Provisioning Protocol (RPP) - The protocol defined in [@!I-D.ietf-rpp-core]." - [ ] C07 L130 "The server MAY constraint the maximum number of `"name"` components supported." -> "An RPP server MAY limit the number of `"name"` components it supports. An RPP server MUST reject an Address that contains more `"name"` components than it supports."
